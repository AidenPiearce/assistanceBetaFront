۲. بررسی وضعیت فعلی کد

این بخش بر اساس خواندن مستقیم کد واقعی دو پروژه نوشته شده است:

  • فرانت‌اند: React + Vite — فایل src/mcp-client.js مستقیماً از مرورگر به سرور MCP وصل می‌شود (اندپوینت‌های /mcp و /ask).
  • بک‌اند: پایتون (Starlette + FastMCP) — فایل src/fpga_mcp/server.py با سه بخش اصلی:
    • ابزارهای MCP (search_notes، lookup_page، list_documents، reindex)
    • اندپوینت /ask: حلقه گفتگو با LLM (سازگار با OpenAI؛ Gemini از طریق OPENAI_BASE_URL) همراه با Tool-Calling و retry روی خطاهای موقت
    • Middleware توکن Bearer و CORS

۳. چرا همه‌چیز باید سمت سرور باشد؟

  1. مرورگر قابل اعتماد نیست. اگر Rate Limit را در فرانت‌اند چک کنید، کاربر می‌تواند اصلاً اپ شما را باز نکند و مستقیم با curl به اندپوینت‌ها حمله کند. تنها جایی که «همهٔ» درخواست‌ها از آن عبور می‌کنند، سرور است.
  2. IP واقعی فقط سمت سرور دیده می‌شود. مرورگر نمی‌داند IP عمومی کاربر چیست؛ پشت Reverse Proxy هم باید هدر X-Forwarded-For را سمت سرور درست تفسیر کرد.
  3. مصرف توکن فقط بعد از تماس با LLM معلوم می‌شود. پاسخ هر درخواست به Gemini فیلد usage دارد (توکن ورودی/خروجی). این تماس داخل _llm_chat در بک‌اند اتفاق می‌افتد؛ پس ثبت آن هم فقط همان‌جا ممکن است.
  4. منبع حقیقت (Source of Truth). آمارِ ثبت‌شده در دیتابیس سرور، مبنای گزارش به مدیران شرکت خواهد بود؛ داده‌ای که کلاینت بفرستد قابل جعل است.
نقش فرانت‌اند چیست؟ فرانت‌اند فقط «مصرف‌کنندهٔ محترم API» است: پاسخ 429 را با پیام فارسی/انگلیسی و شمارش معکوس نشان می‌دهد و هیچ منطق امنیتی ندارد.

۴. مشکل امنیتی فعلی که قبل از هر چیز باید حل شود

نشتی توکن در باندل مرورگر متغیر VITE_MCP_AUTH_TOKEN موقع Build داخل فایل JS نهایی تزریق می‌شود و عملاً برای همهٔ بازدیدکننده‌ها قابل خواندن است. با این توکن هر کسی خارج از اپ شما می‌تواند بی‌نهایت درخواست بزند و سهمیهٔ LLM شرکت را مصرف/اتلاف کند.

راه‌حل در معماری هدف:

  • فرانت‌اند دیگر هیچ توکن قدرتمندی حمل نمی‌کند.
  • چون همه‌چیز روی یک دامنهٔ داخلی شرکت سرو می‌شود (فرانت + بک‌اند)، مرز اعتماد همان دامنه است؛ بک‌اند با Rate Limit بر اساس IP و Session از خودش محافظت می‌کند.
  • کلید Gemini فقط به‌صورت Environment Variable روی سرور می‌ماند و هرگز به سمت کلاینت نمی‌رود.

۵. معماری هدف

┌────────────────────────────── سرور شرکت ──────────────────────────────┐ │ │ │ [مرورگر کاربران] ── HTTPS ──▶ [Nginx] │ │ │ • TLS │ │ │ • X-Forwarded-For │ │ │ • سرو فایل‌های فرانت (static) │ │ │ • مسیر /admin با محافظت │ │ ▼ │ │ [سرور MCP / FastAPI] │ │ │ │ │ ┌────────────────────┼────────────────────┐ │ │ ▼ ▼ ▼ │ │ [Middleware ها] [/ask + tools] [/admin/api/*] │ │ • RealIP • Gemini call • لاگین JWT │ │ • RateLimiter ◀──┐ • usage ثبت • آمار و گزارش │ │ • RequestLogger │ • tool calls • Block/Unblock │ │ │ │ │ │ ▼ └──────── [Redis: شمارنده + Session] │ │ [PostgreSQL: request_logs, config, admins] │ │ │ │ [اپ React ادمین] ── سرو روی /admin ── فقط بعد از لاگین بارگذاری │ └───────────────────────────────────────────────────────────────────────┘

نکتهٔ مهم: به جای ساخت یک سرویس Gateway جداگانه، middleware ها را داخل خود سرور MCP فعلی اضافه می‌کنیم — چون سرور MCP از قبل Starlette است و افزودن middleware به آن طبیعی و کم‌هزینه است. اگر روزی ترافیک آن‌قدر بالا رفت که نیاز به جداسازی داشتید، همان middleware ها قابل انتقال به یک سرویس مستقل هستند.

۶. جزئیات پیاده‌سازی در بک‌اند

۶.۱. چهار Middleware/هوک جدید (به ترتیب اجرا)

#ناموظیفهجزئیات فنی
۱RealIPMiddleware استخراج IP واقعی کاربر خواندن X-Forwarded-For (اولین IP) با fallback به request.client.host؛ فقط وقتی درخواست واقعاً از Nginx آمده به این هدر اعتماد شود.
۲RateLimiterMiddleware اجرای سهمیه‌ها قبل از پردازش بررسی شمارنده‌ها در Redis (کلیدهای rl:ip:{hash} و rl:sess:{id})؛ در صورت تخلف: پاسخ 429 + هدر Retry-After.
۳RequestLoggerMiddleware ثبت هر درخواست در PostgreSQL زمان، IP هش‌شده، session_id، اندپوینت، status code، مدت پاسخ (latency). ثبت غیرمسدودکننده (async) تا سرعت پاسخ نیفتد.
۴UsageTracker (هوک، نه middleware) ثبت مصرف توکن داخل ask_endpoint بعد از هر _llm_chat: خواندن data["usage"]["prompt_tokens"] و data["usage"]["completion_tokens"] و افزودن به رکورد لاگ همان درخواست.

۶.۲. نقاط اتصال دقیق در کد فعلی (server.py)

# 1) داخل ask_endpoint (خط ~319) بعد از گرفتن پاسخ LLM:

usage = data.get("usage", {})          # ← جدید: استخراج توکن‌ها

# 2) در create_http_app (خط ~449) لیست middleware های Starlette:

starlette_app.add_middleware(RateLimiterMiddleware)
starlette_app.add_middleware(RequestLoggerMiddleware)

# 3) جایگزینی _web_sessions (خط ~202) با Redis:
#    کلید: sess:{session_id}  |  ساختار: List of messages  |  TTL: مثلاً 24 ساعت

۶.۳. انتقال Session ها از حافظه به Redis

  • الان با ری‌استارت سرور، همهٔ مکالمات گم می‌شوند و اگر روزی چند worker/replica اجرا شود، هر worker session های خودش را دارد (تجربهٔ کاربری خراب).
  • با Redis: مکالمه بین ری‌استارت‌ها می‌ماند، بین worker ها مشترک است، با TTL خودکار پاک می‌شود، و همان کلید برای آمار «هر Session چند توکن خورده» استفاده می‌شود.

۷. طرح دیتابیس (PostgreSQL)

۷.۱. جدول اصلی لاگ درخواست‌ها

CREATE TABLE request_logs (
    id                 BIGSERIAL PRIMARY KEY,
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    session_id         TEXT,
    ip_hash            TEXT NOT NULL,        -- SHA-256(ip + salt)، نه IP خام
    endpoint           TEXT NOT NULL,        -- '/ask' یا '/mcp'
    tool_name          TEXT,                 -- search_notes / lookup_page / ...
    model              TEXT,                 -- gemini-flash-latest ...
    status_code        INT NOT NULL,
    latency_ms         INT,
    prompt_tokens      INT DEFAULT 0,
    completion_tokens  INT DEFAULT 0,
    total_tokens       INT DEFAULT 0,
    error_flag         BOOLEAN DEFAULT false
);
CREATE INDEX idx_logs_time    ON request_logs (created_at DESC);
CREATE INDEX idx_logs_ip      ON request_logs (ip_hash, created_at DESC);
CREATE INDEX idx_logs_session ON request_logs (session_id, created_at DESC);
چرا IP هش می‌شود؟ ذخیرهٔ IP خام یعنی نگهداری دادهٔ شخصی کارکنان شرکت. با هش + salt، همچنان می‌توانید «این IP همان قبلی است» را تشخیص دهید (برای Block/Unblock و گزارش) ولی در صورت لو رفتن دیتابیس، آی‌پی واقعی افشا نمی‌شود. salt را در Environment Variable نگه دارید.

۷.۴. نمونه کوئری‌های پنل (گزارش‌ها از همین‌جا می‌آیند)

-- مصرف امروز به تفکیک IP
SELECT ip_hash, COUNT(*) AS reqs, SUM(total_tokens) AS tokens
FROM request_logs
WHERE created_at >= date_trunc('day', now())
GROUP BY ip_hash ORDER BY tokens DESC LIMIT 50;

-- روند روزانهٔ ۳۰ روز اخیر (برای نمودار داشبورد)
SELECT date_trunc('day', created_at) AS day,
       COUNT(*) AS requests, SUM(total_tokens) AS tokens,
       AVG(latency_ms)::int AS avg_latency
FROM request_logs
WHERE created_at >= now() - interval '30 days'
GROUP BY 1 ORDER BY 1;

۸.۲. الگوریتم

  • Fixed Window با Redis: کلید rl:ip:{hash}:{yyyymmddhh} با INCR + EXPIRE — ساده، سریع، برای این مقیاس کاملاً کافی.
  • اگر بعداً دقت بالاتری خواستید: Sliding Window (دو شمارندهٔ همپوشان) یا Token Bucket — مفهومش را در مسیر یادگیری بخوانید.

۹. پنل ادمین

۹.۱. معماری

  • API ادمین: مسیرهای /admin/api/* روی همان سرور MCP، با middleware احراز هویت JWT مستقل از API عمومی.
  • UI ادمین: یک اپ React کوچک و جدا (build خروجی‌اش در مسیر /admin روی Nginx سرو می‌شود). از اپ دانشجویان کاملاً جداست.
  • لاگین: صفحهٔ ورود با username/password؛ رمزها به‌صورت bcrypt در جدول admin_users؛ توکن JWT با عمر کوتاه (مثلاً ۳۰ دقیقه) در localStorage.
  • لایهٔ دوم حفاظت: در Nginx می‌توان مسیر /admin را فقط به رنج IP داخلی شرکت محدود کرد (Allowlist) — دفاع در عمق.
  • آینده: اگر شرکت SSO/LDAP دارد، اتصال لاگین ادمین به آن بهترین گزینه است (با تیم IT هماهنگ کنید).

۹.۳. نمودارهای UI

برای رسم نمودار در React از کتابخانهٔ Recharts استفاده می‌شود — سبک، declarative و سازگار با RTL. داده‌اش را از دو endpoint می‌گیرد: /admin/api/stats/daily و /admin/api/stats/today.

۱۰. زیرساخت استقرار روی سرور شرکت

۱۰.۱. چیدمان سرویس‌ها (Docker Compose)

docker-compose.yml ├── nginx : 443/80 ← TLS ، static files (فرانت + پنل ادمین)، proxy_pass ├── mcp-server : uvicorn (FastAPI) — تصویر فعلی Dockerfile با افزودن middleware ها ├── postgres : volume → pg_data ├── redis : volume → redis_data (یا بدون volume، چون فقط شمارنده است) └── backup : cron شبانه → pg_dump + tar از lancedb → مسیر اشتراک شبکه‌ای شرکت

۱۲. مسیر یادگیری — چه چیزهایی را از همین حالا شروع کنم؟

فهرست زیر بر اساس «چه چیزی کدام فاز را باز می‌کند» اولویت‌بندی شده است. برای هر مورد گفته‌ام دقیقاً کدام زیرمجموعهٔ موضوع را یاد بگیرید تا وقت‌تان روی چیزهایی نرود که به این پروژه ربطی ندارد.

اولویت الف — همین هفته شروع کنید (پیش‌نیاز فازهای ۰ تا ۲)

موضوعدقیقاً چه چیزی یاد بگیریدمنبع پیشنهادیزمان
Docker + Docker Compose فوری مفاهیم image/container/volume/network؛ نوشتن یک compose.yml برای app+postgres+redis؛ دیدن لاگ‌ها با logs -f و ورود با exec -it docs.docker.com (بخش Get Started و Compose) ۴–۶ روز
PostgreSQL فوری SELECT/GROUP BY/JOIN، ایندکس گذاشتن، TIMESTAMPTZ، اتصال از پایتون با asyncpg یا psycopg، تهیهٔ dump با pg_dump postgresql.org/docs (tutorial) + تمرین با DBeaver/pgAdmin ۴–۶ روز
Middleware در Starlette/FastAPI فوری نوشتن یک middleware سفارشی ASGI (امضای __call__(scope, receive, send))، ترتیب اجرای middleware ها، پاسخ دادن مستقیم از middleware (همان کاری که BearerAuthMiddleware فعلی شما می‌کند — الگوی خوبی برای تقلید است) starlette.dev/middleware + خواندن همین کد فعلی server.py خط 476 ۱–۲ روز
Nginx به‌عنوان Reverse Proxy مهم proxy_pass، هدرهای X-Forwarded-For/X-Real-IP، سرو فایل static، تنظیم TLS، محدودکردن مسیر با allow/deny nginx.org/en/docs + مثال‌های «nginx reverse proxy fastapi» ۲–۳ روز

اولویت ب — قبل از استقرار نهایی

موضوعدقیقاً چه چیزی یاد بگیریدمنبع پیشنهادیزمان
Redis مهم فقط این الگوها: INCR، EXPIRE، TTL، ذخیرهٔ List برای history گفتگو؛ کتابخانهٔ redis-py در حالت async redis.io/docs (بخش data types) ۲–۳ روز
الگوریتم‌های Rate Limiting مهم تفاوت Fixed Window / Sliding Window / Token Bucket؛ اینکه چرا Fixed Window در مرزش پنجره جهش دارد؛ مطالعهٔ هدرهای استاندارد Retry-After جستجو: "rate limiting algorithms stripe blog" و "Kong rate limiting" ۱ روز مطالعه

۱۳. تصمیمات باز (برای شروع اجرا باید روشن شوند)

  1. سرور شرکت: آیا سرور لینوکسی آماده دارید یا باید درخواست کنید؟ چه توزیعی (Ubuntu/RHEL)؟
  2. PostgreSQL و Redis مرکزی: تیم IT سرویس آماده می‌دهد یا داخل Docker Compose خودمان بالا می‌آوریم؟ (پیش‌فرض سند: داخل Compose خودمان.)
  3. دامنه و TLS: نام دامنهٔ داخلی چیست و گواهی را تیم IT می‌دهد یا Let's Encrypt؟
  4. SSO/LDAP: آیا شرکت سامانهٔ ورود یکپارچه دارد که پنل ادمین به وصل شود؟
  5. سقف بودجهٔ LLM: مقدار واقعی «توکن در روز» که شرکت حاضر است پرداخت کند چیست؟ (عدد پیشنهادی سند موقتی است.)
  6. Retention لاگ: چند ماه لاگ نگه داریم؟ (پیشنهاد: جزئیات ۹۰ روز، گزارش تجمیعی روزانه برای همیشه.)
